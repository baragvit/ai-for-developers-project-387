# REVIEW.md

Review criteria for pull requests in this repository. The independent reviewer in
[`.github/workflows/opencode-review.yml`](.github/workflows/opencode-review.yml) gets this file with every review
(from the base branch); humans use it too. The project rules are in [`AGENTS.md`](AGENTS.md), the product rules in
[`README.md`](README.md).

## What a finding looks like

Report only defects you can confirm from the code, the diff or the CI results. Each finding has:

- **file and line**: `path/to/file.ts:42` in the PR head;
- **condition**: input or sequence of actions that triggers the error;
- **consequence**: what the guest, the owner, CI or the agent gets wrong;
- **severity**: `blocker` (breaks a rule below or the spec), `major` (wrong behavior in a real case), `minor`.

If there are no confirmed defects, write exactly that: «Подтверждённых дефектов не найдено». Do not invent findings
to fill the review. Formatting and style are checked by oxlint and tsc: do not repeat their output. Questions and
suggestions go in a separate short section, not as findings.

## Calendar rules a change must not break

- **A taken slot never stays bookable.** Two bookings never overlap, even for different event types. Every path that
  creates a booking goes through the overlap check; the conflict answer is `409 SLOT_TAKEN`. Concurrent requests for
  one slot give one success and one conflict.
- **Intervals are half-open.** A booking ending at 10:00 does not block a slot starting at 10:00; adjacency is allowed.
- **Slots**: a 14-day window, working days and hours in the owner's time zone (`OWNER_TIMEZONE`), the duration grid,
  no slots that already started, correct across DST changes. Time comes from the injected clock, never `Date.now()`
  in logic.
- **Times** travel over the API as ISO 8601 UTC; the frontend renders them in the viewer's time zone.
- **Design First**: behavior changes start in `api-contract/main.tsp`; generated files (`api-contract/openapi.yaml`,
  `frontend/src/api/schema.d.ts`, `backend/src/api/model/`) are regenerated by `npm run contract`, never edited by
  hand. The frontend reaches the API only through `frontend/src/api`.
- **Layers**: services take and return primitives, domain types or `Result`, never API DTOs; DTO ↔ domain mapping
  lives in `backend/src/api/`.
- **Validation**: invalid input gives `400 VALIDATION_ERROR` with a per-field error in `details`, in Russian; the
  invalid entity is not created.
- **User-supplied URLs** rendered as links are `http`/`https` only (no `javascript:` or `data:`), open in a new tab
  with `rel="noopener noreferrer"`, and an absent value renders no empty block.
- UI copy is in Russian; code, identifiers and comments in English.

## Tests

- Each acceptance scenario of the spec (main, negative, neighbor) has a test at the boundary from the AGENTS.md table:
  API tests through `injectChecked`, components on the mocked client, Playwright on the real server without
  `page.route`.
- A test must fail without the new behavior. Assertions that pass on the old code (only "no error", only status 200)
  do not cover the scenario.
- Conflict tests stay in `backend/test/booking-conflicts.test.ts`, and `scripts/rule-guard/expected-failures.txt`
  lists every test that must fail with the overlap check patched out.

## Depth of review by risk

The consequences of a mistake decide the depth, not the number of changed lines.

| Change | What to check before merge |
| --- | --- |
| Label, copy, layout | Matches the task text; shows up in the UI (component test or browser check) |
| Slot calculation, booking, overlaps | Main scenario, overlapping bookings, adjacent and neighbor cases, concurrent requests |
| Contract, validation, stored fields | Generated files in sync, old clients unaffected (optional fields), error codes |
| GitHub Actions permissions, secrets, tokens, triggers | Access to code and secrets, fork PRs, `pull_request_target`; a separate human decision |

Check the PR description: linked request, spec, tickets and human approval; `Closes #N` for the closed tickets;
checks with commands, run links and the checked SHA; risk and rollback filled in for this change. A missing link, or a
change outside the approved spec and tickets, is a finding.

## Repeat reviews

Findings the human already settled in the PR discussion (fixed, or rejected with a reason) are not raised again unless
a new commit brings the problem back. A repeat review checks the new commits and the behavior they touch.
